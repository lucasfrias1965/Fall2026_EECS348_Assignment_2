## 1. CRITICAL: `human.c` fails the assignment's own Sample Test File

I compiled `human.c` and ran it against the exact Sample Test File from `Assignment 2 Instructions.md`. The second `NEXT` is wrong:

```
Expected: Sender: Boss / Subject: Important / Date: 12-20-2024
Got:      Sender: ImportantPerson / Subject: Health Insurance Enrollment / Date: 12-31-2024
```

**Root cause, don't just patch the symptom — understand it first:**

- `Email` (human.c:47-52) has *two* separate priority-related fields: `category` (the `enum Sender`) and `categoryRank` (an `int`, left over from Sonnet's version).
- `parseEmailFields` (human.c:347) sets `outEmail->category = categoryRank(category);` but **never touches `outEmail->categoryRank`**. Since `email` is an uninitialized stack variable in `handleEmailCommand`, that int field is garbage.
- `emailHasHigherPriority` (human.c:142-147) compares `a->categoryRank` / `b->categoryRank` — the garbage field — before ever looking at the date. That's why ordering looks almost-random for anything beyond the first item.

**Why the obvious fix ("just compare `category` instead") isn't a one-line swap either:** your `enum Sender` (human.c:36-43) is declared `Unknown, Boss, Subordinate, Peer, ImportantPerson, OtherPerson` — so `Boss == 1` and `OtherPerson == 5`. `emailHasHigherPriority` treats a *larger* number as higher priority, so comparing the enum directly would rank `OtherPerson` above `Boss` — backwards. You need either:
- a real rank lookup (map enum → priority integer, the way Sonnet's original `categoryRank(const char*)` did), or
- reorder the enum so ordinal value already matches priority and flip the comparison direction consistently.

Also rename one of the two things called `categoryRank` (the function and the now-dead struct field) — reusing the identical name for a function and an unrelated struct member compiles fine in C but is exactly the kind of thing that hides bugs like this one during review.

**Before you touch anything else:** fix this, then re-run against the Sample Test File until the output matches exactly (including the `COUNT` after two `READ`s). This is 30 rubric points and it's currently failing verifiably, not hypothetically.
